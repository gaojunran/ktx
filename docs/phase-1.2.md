# Phase 1.2：lockfile + `--frozen` + `kts add`

> 时间：2026-05-31
> 主题：把 ktor 样例的"二次启动 8 秒"压回亚秒，让 CI 不联网也能跑

## 这一波要解决什么

Phase 1.1 上线后，**编译产物缓存命中**的脚本二次启动只要 220ms。但 ktor 样例（10+ 传递依赖）二次仍 8.2 秒，原因是：即便编译缓存命中，main-kts 仍走一遍 `MainKtsConfigurator → MavenDependenciesResolver → Aether` 来确认依赖位置。这一步在网络好时也要 0.5-数秒，在 CI / 网断时直接卡死。

Phase 1.2 的目标：**记录依赖解析结果，下次跑时绕过 Aether**。这是 uv `lock + run --frozen` 同款语义。

## 关键事实（调研得到的）

走 Explore agent 把 main-kts resolver 的 hook 点摸清：

| 项 | 结论 |
|---|---|
| `ExternalDependenciesResolver` 接口 | `acceptsArtifact / acceptsRepository / resolve（单+批） / addRepository`，五个方法 |
| `resolve` 输出 | `ResultWithDiagnostics<List<File>>`（已是绝对路径） |
| 默认 resolver 链 | `CompoundDependenciesResolver(FileSystemDependenciesResolver(), MavenDependenciesResolver())` |
| `MainKtsConfigurator` 构造 | 接受任意 `ExternalDependenciesResolver`，默认值就是上面那个链 |
| 本地仓库位置 | `~/.m2/repository`（标准 m2 布局） |
| 批量 `resolve` | 在 `MavenDependenciesResolver` 里被覆写为一次性 Aether 调用，无法按坐标拆 |

最关键的发现：**hook 点干净**，`MainKtsConfigurator(resolver)` 直接换 resolver，不需要 fork，不需要改主流程。

## 设计

```
正常 run：       Compound(FileSystem, Recording(Compound(FileSystem, Maven)))
                                        ↑
                                旁路记录每次 resolve 的输入输出

kts lock：       同上 + 跑完后写 <script>.kts.lock，且：
                 - 替换脚本主体为 `Unit`（避免副作用）
                 - 临时清空缓存目录（确保 RecordingResolver 拿到记录）

kts run --frozen: Compound(FileSystem, Frozen(lockfile))
                                       ↑
                              只查 lockfile，不接网
```

### Lockfile 格式（TOML）

```toml
# Auto-generated by ktx. Do not edit by hand.
schema = 1

[script]
hash = "74f954cf9d7ba59ade2e2069b829acc4ceca6671c6e3254fcdaae629b0498010"

[[directs]]
coordinates = "com.fasterxml.jackson.core:jackson-databind:2.18.0"
files = [
  "com/fasterxml/jackson/core/jackson-annotations/2.18.0/jackson-annotations-2.18.0.jar",
  "com/fasterxml/jackson/core/jackson-core/2.18.0/jackson-core-2.18.0.jar",
  "com/fasterxml/jackson/core/jackson-databind/2.18.0/jackson-databind-2.18.0.jar",
]
```

存「相对 m2 仓库」的路径，跨机器可移植。frozen 模式拼接 `~/.m2/repository/<rel>` 拿 jar。

## 关键设计决策

### 1. ThreadLocal 注入 resolver

`@KotlinScript` 注解要求 `compilationConfiguration` 是 0 参可实例化的 class，没法通过构造器注入 resolver。最初用「另写一个 `buildKtsCompilationConfig(resolver)`」的方式独立构造完整 config，结果遇到 `KtsScript(args)` 的构造参数找不到——因为 `createJvmCompilationConfigurationFromTemplate<KtsScript>(...)` 模板里隐式注入了 `baseClass = KtsScript`，手搓 config 时丢了这一信息。

折中方案：在 `KtsScriptDefinition` 这个无参 class 内部读 ThreadLocal，调用方在 `eval` 之前 set。

```kotlin
class KtsScriptDefinition : ScriptCompilationConfiguration({
    refineConfiguration {
        val resolver = resolverOverride.get()  // ← ThreadLocal
        val configurator =
            if (resolver != null) MainKtsConfigurator(resolver) else MainKtsConfigurator()
        onAnnotations(...)
    }
})

inline fun <T> withResolverOverride(resolver: ExternalDependenciesResolver?, block: () -> T): T {
    val prev = resolverOverride.get()
    resolverOverride.set(resolver)
    try { return block() } finally { resolverOverride.set(prev) }
}
```

不优雅，但脚本编译是「一次一脚本一线程」的场景，ThreadLocal 完全够用。Phase 2 上 daemon 后每个请求一个 worker 线程，仍然适用。

### 2. lock 时必须绕过编译产物缓存

第一版实现忘了这一点：lock 流程跑完后 `RecordingResolver.snapshot()` 是空的。原因：main-kts 编译产物缓存命中后**不再调 resolver**——非常合理（jar 已存在不需要重新解析）—— 但 RecordingResolver 也就拿不到记录了。

修法：lock 时把缓存目录系统属性临时设为空字符串（main-kts 内部 `cacheExtSetting.isBlank() -> null` 直接禁用缓存）。run-with-bypass 跑完后立刻恢复。

```kotlin
val origCacheDir = System.getProperty(MAIN_KTS_CACHE_DIR_PROPERTY)
if (bypassCompiledCache) System.setProperty(MAIN_KTS_CACHE_DIR_PROPERTY, "")
try { /* eval */ } finally {
    if (bypassCompiledCache) {
        if (origCacheDir != null) System.setProperty(MAIN_KTS_CACHE_DIR_PROPERTY, origCacheDir)
        else System.clearProperty(MAIN_KTS_CACHE_DIR_PROPERTY)
    }
}
```

### 3. lock 时替换脚本主体为 `Unit`

uv lock 不会执行脚本本身，因为 PEP 723 元数据可独立解析。我们的 `@file:DependsOn` 必须经编译器解析才能触发 resolver，所以**编译流程要走完**——但脚本主体应该不被执行（避免副作用，如发 HTTP 请求）。

实现：找到「脚本主体开始」的位置（第一个非 shebang / 非空 / 非 `//` / 非 `@file:` 的行），从那里截断换成 `Unit`。这样 main-kts 仍走依赖解析（注解保留），但脚本主体什么都不做。

### 4. TOML 顶层 key 必须写在所有 `[table]` 之前

写 lockfile 时第一版把顶层 `repositories = [...]` 放在了 `[script]` 之后——TOML 解释为 `script.repositories`（嵌入到 `[script]` table 里），读出来全空。

TOML 规则：一旦进入一个 table，后续 key 都属于该 table 直到下一个 `[...]` 标头。修法：把 `repositories` 移到 `schema` 后、`[script]` 前。

## 性能数据

`samples/jackson.main.kts`（含 jackson-databind + 3 个传递依赖，无 HTTP 请求干扰）：

| 场景 | 用时 |
|---|---|
| 首次冷启（无缓存 + Aether 联网） | 6.76s |
| 二次跑（编译缓存命中） | 280ms |
| 二次 `--frozen`（缓存命中 + 跳过 Aether） | 300ms |
| 新机器场景：lockfile 在但**编译缓存被清** ||
| ─ 在线 `run`（Aether + 全编译） | 6.72s |
| ─ `--frozen`（lockfile + 全编译） | **1.64s** |

**核心场景**：CI 拉新代码、`~/.m2` 已被缓存（如 GitHub Actions 的 maven cache action），`kts run --frozen` 起步 1.6s——**比在线 run 快 4 倍**，且不联网。

## 这一波撞到的坑

**`MainKtsConfigurator` 构造接收 resolver，但 `@KotlinScript` 不允许。**
@KotlinScript 注解 `compilationConfiguration = X::class` 要求 X 无参可构造。最初想直接「构造时传 resolver」失败。最终用 ThreadLocal 旁路。

**手搓 ScriptCompilationConfiguration 丢失 baseClass。**
试图绕开 ThreadLocal 用 `ScriptCompilationConfiguration { ... }` 直接构造，结果 `KtsScript(args)` 的构造参数找不到，编译器报「wrong number of arguments: 1 expected: 0」。原因是模板派生 `createJvmCompilationConfigurationFromTemplate<KtsScript>(...)` 时隐式注入了 baseClass，手搓时丢了这一关键信息。教训：**优先用 `createJvmCompilationConfigurationFromTemplate` + 旁路注入，不要重新组装 config**。

**lock 时编译产物缓存命中导致 RecordingResolver 是空的。**
main-kts 缓存命中后跳过 resolver，旁路记录拿不到任何东西。修：lock 时临时设 system property 为空字符串禁用缓存（main-kts 内部 `cacheExtSetting.isBlank() -> null` 路径）。

**`inline` + `internal` 不兼容。**
`withResolverOverride` 写成 `inline` + 访问 `internal val` 不让过。给 internal 加 `@PublishedApi` 解决。

**TOML 顶层 key 顺序敏感。**
`repositories = [...]` 写在 `[script]` 之后会被吞进 `script.repositories`。TOML 一旦进入 table 就出不来——必须把所有顶层 key 放在所有 `[...]` 标头**之前**。

## 已知遗留 / 下一波要做的

1. **`@file:Toolchain` 的 `jdk` 字段还没真用**——等 Phase 1.3 `kts toolchain install` 做 Adoptium 下载后接通。
2. **lockfile 没记录 jar 的 sha256**——Phase 1.x 后期可加，做完整性校验。
3. **没有 `kts cache info / clean`** 子命令——下一波随手加。
4. **lockfile 与 m2 强耦合**：依赖必须在 `~/.m2/repository` 下。如果用户 jar 在别的 Maven mirror（如阿里云），目录布局相同所以无影响；但若是 Gradle cache（`~/.gradle/caches`）布局不同，frozen 模式会报错。这是我们故意的限制（保持简单），用户可手动 `mvn dependency:get` 预填充。

## 总结

CLI 表面从 4 命令扩到 7 命令（含选项），核心场景（CI 新机器拉代码 + `kts run --frozen`）从 6.7s 降到 1.6s。这一波的关键设计是**找对 hook 点**：

- `ExternalDependenciesResolver` 是 main-kts 暴露给我们的唯一 hook 点，但它**完全够用**——记录解析结果是 `RecordingResolver` 的事，离线返回是 `FrozenResolver` 的事。
- `MainKtsConfigurator(resolver)` 直接换 resolver，整个 main-kts 注解处理流程纹丝不动。

整个 Phase 1.2 几乎没改动 main-kts 的语义，仅仅是「在它的解析路径上插了个观察者 / 替换了真实 resolver」。
